# 本专业小型工具调用 Agent 设计与对比实验

《人工智能的网络应用》课堂作业 ｜ 基于课程示例 `6-agent/3-prog` 完成

## 1. 任务说明

**任务**：定位"切了代理节点，出口 IP 却没变"这一类问题。输入是现象描述、直连与走代理两次 `curl` 的原始输出、以及本机当前生效的分流规则；输出是结论（根因，或卡在哪一层）、支撑结论的原始证据、下一步建议、本次未覆盖的检查项。

**为什么和我的课题相关**：这是我自己真实遇到的问题——宿舍 Windows 笔记本上 Clash Verge 切了节点，浏览器查出口 IP 还是原来的。它属于课程项目里"网络 Incident 调查"这一类，此前已经用 office hour 流程做过完整选题与设计，这次是把这个课题切出一小块，做成一个可运行的最小工具调用 agent。

**为什么这个任务需要工具**：判断"两次出口 IP 是否相同"和"查询站是否被分流规则拦掉"都是确定的事实题，不该由模型凭印象回答。尤其第二条——如果查询站本身被规则 REJECT 掉，工具测不到任何 IP，模型很容易得出"代理坏了"这个完全错误的结论。这正是我把任务限定在这两点上的原因。

## 2. 工具设计

新增两个工具（`my-agent-demo.py`），一个负责计算，一个负责规则判断：

| 工具 | 类型 | 参数 | 返回 |
|---|---|---|---|
| `compare_exit_ip(direct_trace, proxy_trace)` | 计算 | 两段 `curl` 原始输出全文 | `direct_ip / proxy_ip / parsed / same_ip / note` |
| `check_probe_blocked(domain)` | 规则判断 | 查询站域名 | `matched / rule / proxy / verdict / note`，`verdict ∈ {blocked, direct, proxied}` |

**为什么这样拆**：

- 两件事互不重叠：一个是"把两段文本里的数字提出来比对"，一个是"在一个有序规则表里做匹配"。分开之后各自可以单独验证（脚本里的 `--selftest` 就是这两个纯函数的断言）。
- `compare_exit_ip` 专门返回 `parsed` 这个字段：**解析不到 IP 时 `parsed=False`，而不是 `same_ip=True`**。"测不到"和"出口没变"是两件事，把它们合并成一个布尔值，正是这个任务里最容易出错的地方。
- 规则列表**没有**做成工具参数。真实的规则有 66 条，让模型把整张表复述成参数必然出错；规则由采集器侧提供，模型只传一个域名。工具的接口形状要按模型的可靠性来定，而不是按"函数式纯粹"来定。
- 故意保留了边界：`IPCIDR / RuleSet / AND` 这几类规则需要真实请求上下文才判得准，工具不猜（代码里留了 `ponytail:` 注记，说明真实采集器里由内核日志补这一层）。

## 3. 结果对比

三个场景（材料全部来自本机实测）× 两种模式，共 6 次运行，原始记录在 `outputs/comparison.md`：

| 场景 | 期望判断 | 无工具 | 有工具 |
|---|---|---|---|
| `ok` 一切正常 | 未发现问题，不许硬凑根因 | 判对，但结论啰嗦，掺了无关建议 | 判对，两个工具都调了，结论直接引工具返回 |
| `same` 出口真没变 | 出口确实没变 | 判对，但**把 `ip=` 原始输出引成了 JSON**，还建议 `kill -9`、`ss -tuln`（Windows 上都没有） | 判对，而且发现"规则明明命中代理、出口却没变"这对矛盾 |
| `blocked` 测量被拦 | 测量被规则拦掉，不是代理坏了 | 结论恰好说对了，但把直连那次也解释成"被规则拒绝"——直连根本没进规则引擎 | 判对，直接引用工具返回的 `verdict=blocked` |

**没有工具时，模型容易错在哪**：一是编造证据的格式，把 `ip=183.242.199.247` 这种键值行引成 `{"ip": "...", "colo": ...}`，看起来像在引用原文，其实原文里没有；二是给越界建议，Windows 上不存在 `ss`、`kill -9`；三是"测不到"和"没变"混着说；四是每次都写得很长很自信，结论对错反而不好判断。

**有工具后哪些地方变稳了**：数值和字段都有确定的出处，不再需要"相信模型的引用"；`same` 场景里模型同时拿到两个工具的返回，能指出"规则命中代理但出口 IP 相同"这个矛盾，这一步无工具时做不到；输出明显变短，因为不用再把原始材料重抄一遍。

**仍然还有哪些错误**：`blocked` 场景两次运行，模型都建议"换一个查询站，比如 `ipapi.co` / `ipwho.is`"——而这两条在同一个规则列表里也是 `REJECT`。工具只回答了"这个域名会不会被拦"，模型没有把"候选查询站是否可用"也交给工具。这条错误的根源是工具给的是单点查询，而模型需要的是筛选，属于接口设计问题，不是模型问题。

另外，用 `qwen3:0.6b` 跑课程示例时，模型反复填不对工具参数，直接触发 `Tool 'analyze_wireless_link' exceeded max retries count of 1`。**工具调用对模型能力有下限**，这是本次实验里最直接的一条边界。

## 4. 工程分层理解

- **prompt**：交代任务和纪律（每条结论必须能指回原始输出、区分"测不到"与"没走代理"、没问题就直说没问题）。它决定"该不该调工具、按什么顺序调"，但不负责算对。
- **tool**：把确定的事从模型手里拿走——解析、比对、规则匹配，返回稳定的结构化结果。工具是"可信的少数事实"的来源。
- **模型接入层**：`OpenAIProvider` + `OpenAIChatModel` 把本地 Ollama 的 `/v1` 接进来。这一层只解决"怎么和模型说话"，换模型、换服务商只动这里，工具和任务逻辑一行都不用改。这也是课程里 `6-agent/2-prog` 和 `3-prog` 的差别所在：接口一旦兼容，这一层就从两百行变成十来行。
- **workflow / 终止条件**：本任务里是最小的那种——`run_sync` 一次调用，模型自己决定调几次工具，工具返回后继续，直到给出最终文本。没有额外的状态机，因为检查项只有两个，编排本身不产生价值。
- **evaluation**：判定不写在程序里，而是写在三个预先定死的场景和各自的"期望判断"上，跑完人对照 `outputs/comparison.md`。第 `ok` 条是最重要的一条，它是专门用来测幻觉的：什么都没坏的时候，它敢不敢说什么都没坏。

## 5. context / memory / state

**用到的当前上下文**：现象描述、两段 `curl` 原始输出、12 条分流规则片段、以及两个工具的返回值。全部放进一次 prompt，没有跨轮状态。

**如果以后要跨多轮保留经验**：值得做成 memory 的是"这台机器的稳定事实"——客户端类型与版本、代理端口、控制器地址、规则快照，以及历次诊断的结论。理由是采集一次要几秒到十几秒，而重复采集的结果基本不变，每次重采是纯浪费。

**这一步为什么现在先不急着做**：这次任务一次调用就能判完，加 memory 只会引入"记忆过期"这个新的错误来源——比如规则改过之后，旧的规则快照会让判断更错。等到真的要做"对照诊断"（两台机器、同一份订阅、表现不同）时，跨机器的差异才有必要被记住，那时候再引入。

## 附：怎么复现

```bash
pip install "pydantic-ai-slim[openai]"   # 只装 OpenAI 适配，避免全量依赖回溯
ollama pull qwen3:4b

python 0-pydanticai-openai-comm-agent.py --model qwen3:4b   # Part A：跑通课程示例
python my-agent-demo.py --selftest                          # 两个工具的自检
python my-agent-demo.py --case blocked                      # Part B/C：有工具
python my-agent-demo.py --case blocked --no-tools           # Part D：无工具对照
python my-agent-demo.py --all                               # 2 种模式 x 3 个场景
```

两处环境适配（记录在案，便于老师复核）：Windows 控制台默认 GBK，需要 `PYTHONIOENCODING=utf-8`，脚本内部也做了 `stdout.reconfigure`；pydantic-ai 2.x 起 `result.usage` 从方法变成属性，课程示例里对应一行做了兼容。
