# 设计文档 v2：AI 代理异常诊断助手

日期：2026-09-16 ｜ 版本：v2 ｜ 状态：已确认（2026-09-16）

> v1 的内核是一个规则引擎工具，AI 被明确排除在外。课程要求是"应用 AI 做一个网络相关的应用"，
> 所以 v2 把 AI 提到主线：确定性检查由脚本做，需要"理解"的部分交给模型。

## 一、用户目标

输入"切了代理节点、出口 IP 却没变"这个症状，工具自动采集本机证据，
由大模型按网络分层模型自主排查，输出根因判定和支撑它的原始证据；
证据不足时，输出"卡在哪一层、还缺什么证据"。

一句话：**让 AI 像人一样排查一个网络问题，而不是像搜索引擎一样回答问题。**

## 二、关键用户场景

1. **自用（主场景）**：宿舍 Windows 笔记本，切了节点，浏览器查 IP 还是本地地址。
   跑一条命令，几分钟内拿到结论和证据。
2. **对照（室友）**：同一份订阅、同样症状，用同一工具跑，确认不是个例。
3. **验证（自己造故障）**：故意关掉系统代理 / 把模式切成 DIRECT / 停掉客户端进程，
   看它能不能分别判出来。这是"判定准不准"唯一的证据来源，也是课程验收时的底气。
4. **验收（课程）**：老师或助教看到它自主决定查什么、结论引用证据、
   不确定时敢说自己不确定。

## 三、范围边界

- **平台**：只做 Windows。用到注册表代理设置、`netstat -ano`、`curl.exe`
- **客户端**：不绑定某一款。采集器先"发现"客户端（扫已知配置目录），
  再从系统代理注册表读实际端口，再从发现到的配置目录里取日志与分流规则
- **入口症状**：只处理"节点切换成功但出口 IP 未变"这一类，不处理断流、卡顿、DNS 污染
- **根因覆盖**：接管层 / 规则层 / 网络层 / 测量层，四层
- **只读**：工具不修改系统设置、不自动修复、不重启客户端
- **依赖**：需要访问大模型 API；网络不通时退化为"只采集不判定"
- **时间盒**：14 小时（1 小时/天 × 14 天）

## 四、不做什么

- 不做 GUI
- 不做离线硬编码判定表（判定交给模型）
- 不自动修复、不改系统配置、不重启客户端
- 不抓包（不做 Wireshark 那一套）
- 不覆盖 macOS / Linux
- 不做服务端、多用户、数据库
- 不在没有证据引用的情况下输出结论
- 不做"假设/证据工作台"式的记事本

## 五、主要行为

入口：`python vpn_diag.py`，无需参数。

行为分三步：

1. **采集器**暴露一组只读检查项：系统代理设置 / 端口与属主进程 / 代理客户端进程 /
   直连与走代理的出口 IP（v4、v6 各一次）/ 本机全局 IPv6 地址 /
   客户端日志尾部 / 分流规则配置
2. **模型自主编排**：它决定先查哪一项、拿到结果后决定下一步查什么，
   直到能下结论，或者确认自己判不出来
3. **输出固定四段**：结论（根因，或卡在哪一层）｜证据（带原始输出引用）｜
   下一步建议｜本次未覆盖的检查项

### 两道缰绳（设计上的硬约束）

- **分层纪律**：必须按 接管层 → 规则层 → 网络层 → 测量层 的顺序排除，
  上一层没有证据，不许往下走
- **证据绑定**：每条结论必须引用具体检查项的输出，引用不了的结论不许输出

### 确定性与 AI 的分工

| 交给脚本（二值事实，AI 不许推翻） | 交给模型（需要理解的事） |
|---|---|
| 端口有没有在监听、属主是谁 | 读懂客户端日志在说什么 |
| 两个出口 IP 是否相同 | 读懂分流规则配置的意图 |
| 系统代理开关的实际取值 | 从杂乱证据里提出"下一步该查什么" |
| 本机有没有全局 IPv6 地址 | 把证据组织成一条能讲给人听的推理链 |

### 实现形态

Python 单文件 + 采集器模块（Python 重写，用标准库 `winreg` 读注册表、
解析 `netstat -ano` 拿端口与属主，不引入第三方系统库）。
大模型通过官方 SDK 的 tool-use 调用检查项，`base_url` / `model` / `key` 全部走环境变量。
上一轮那份 `vpn-check.ps1` 草稿作废，其中的采集逻辑搬进 Python。

客户端适配表（只列已知路径，扫到哪个用哪个）：

| 客户端 | 配置/日志目录 | 默认混合端口 |
|---|---|---|
| Clash for Windows | `%USERPROFILE%\.config\clash`（`logs/`、`profiles/`） | 7890 |
| Clash Verge Rev | `%APPDATA%\io.github.clash-verge-rev.clash-verge-rev`（`logs/`、`profiles/`、`config.yaml`） | 7897 |
| Clash Verge（旧版） | `%APPDATA%\clash-verge` | 7897 |
| Mihomo Party | `%APPDATA%\mihomo-party` | 7890 |

端口一律以系统代理注册表里的实际值为准，上面这列只用于在注册表读不到时的兜底。

## 六、风险与未定问题

1. **幻觉（最大风险）**：模型会一本正经地编造根因。
   缓解＝分层纪律 + 证据引用 + 二值事实由脚本判定。
   验收时要专门测一条：**证据不足时它敢不敢说"我不知道"**。
2. **API 的可达与成本**：一次诊断会触发多轮调用。key 走环境变量，不写进代码。
3. **死循环风险**：你是在代理出问题的时候用这个工具，而它需要访问 API。
   如果 API 直连不通，你得先修代理——所以优先选国内可直连的模型服务。
4. **客户端差异（已降级）**：原方案按具体客户端写死路径，风险较高。
   改为"自动发现 + 适配表"后，风险降为"遇到表外的客户端"——
   此时工具应当明说"没找到客户端配置目录"，而不是继续猜。
   已在开发机上核实：Clash Verge Rev 的目录结构与端口（7897）与表中一致。
5. **时间盒**：采集器约 4h、AI 编排约 5h、验证与修 bug 约 4h、缓冲 1h。
6. **未定**：具体模型与 base_url；是否需要"向用户追问"的交互模式；本机 Python 环境是否就绪。

## 七、确认结论

- 客户端：Clash Verge（在本机上核实到的具体版本为 Clash Verge Rev，
  配置目录 `%APPDATA%\io.github.clash-verge-rev.clash-verge-rev`）。
  适配表同时覆盖 Verge 旧版路径与端口，无需再区分
- 平台：Windows
- 交付与验证环境：本机
- 本机 Python：3.12.6 可用（`python` / `py` 均可调用）
- 设计草案无待改项，v2 冻结
