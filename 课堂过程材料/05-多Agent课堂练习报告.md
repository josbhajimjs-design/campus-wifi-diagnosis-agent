# 单 Agent / 双 Agent / manager + specialists 对比分析

> 学号：23211053　姓名：谢鑫强　课程：多 Agent 系统
> 依据：两套课程示例、本地 CrewAI 1.15.22 源码及上午保存的三次运行结果。结构图单独附在 `结构图.png`，详细证据见 `运行记录.md`。

## 1. 两套示例的核心区别

| 维度 | 单 Agent（结构参照） | 2-prog 双 Agent | 4-prog manager + specialists |
| --- | --- | --- | --- |
| 设计分工 | 同一个角色计算、判断并收口 | 分析员计算，顾问提出建议 | 经理规划与收口，两类专家提供计算与建议 |
| 任务结构 | 一个任务内调用工具 | analysis → advice，2 个任务 | planning → budget → modulation → final，4 个任务 |
| 信息交接 | 同一执行上下文 | advice 显式接收 analysis 输出 | budget 接收规划；modulation 接收规划与预算；final 接收前三步 |
| 调度 / 记忆 | 视实现而定 | sequential；未加载项目记忆 | hierarchical；记忆内联到规划和最终任务 |

双 Agent 将单 Agent 内部的“先算后判”变成显式角色分工与任务交接，便于分别配置工具和检查中间结果；4-prog 的设计再增加规划、汇总和项目经验。hierarchical 适合由经理组织工作、按需委派的意图，但能否形成实际协作还要看执行轨迹。

**本地实测与设计意图有差别。** 4-prog 四个任务的输出执行者均为“通信项目经理”，保存的消息显示经理直接调用计算与调制工具，未见专家委派。核对框架发现 hierarchical 的任务执行入口选择 manager，而非直接选择 `task.agent`。因此本次证明的是“经理执行四阶段流程”，不能据此宣称已验证“两个专家独立执行、经理复核”。代码中的专家绑定不等于实际执行者。

## 2. process、context、memory 各管什么

- **process 管执行策略。** sequential 按任务列表顺序选择绑定角色；本地 hierarchical 将任务交给 manager，由其组织执行或委派。它不等于自动并行。
- **context 管本次任务的信息交接。** 显式指定哪些前序任务输出进入当前任务；本例按已排好的依赖传递文本，不是共享全部历史。任务顺序仍需与依赖相容。
- **memory 管跨运行可复用的背景经验。** 本例用 `Path.read_text()` 读取 `project_memory.md`，将稳定性与输出偏好拼进规划和最终任务描述；没有注册 `read_project_memory` 工具，也没有自动学习或写回。它是人工维护的持久背景，不是本次任务交接。

## 3. 实测结果、收益与代价

同题、同模型 `qwen3:4b` 的已保存结果如下；请求数按输出中的 `successful_requests` 统计，不等同于任务数，也未独立核验 HTTP 请求次数。

| 版本 | 任务数 | 框架报告请求数 | 框架报告 tokens | 主要调制建议 |
| --- | ---: | ---: | ---: | --- |
| 双 Agent | 2 | 8 | 22,234 | QPSK 更稳，16QAM 可尝试 |
| 经理流程，有 memory | 4 | 18 | 45,528 | 同上 |
| 经理流程，无 memory 相关段落 | 4 | 18 | 41,136 | 同上 |

三次关键数值一致：SNR 15.352 dB，Shannon 容量 102.825 Mbps。经理版本 token 约为双 Agent 的 **2.05 倍**；这是本题单次观测，不能推出普遍倍数、耗时或失败率。相同数字来自相同确定性工具，也不能证明多 Agent 更准确。

**memory 对照的边界：** 去掉记忆及相关输出要求后，主要建议未变；工具本来就返回“16QAM 可以尝试，QPSK 更稳”，任务里也仍要求保守判断。因此不能把保守结论归因于 memory。实验还改变了输出要求、每种条件仅运行一次，只能观察本次表述与 token 差异，不能证明记忆提高了质量。

**收益**是职责和中间结果更容易检查，以及具备设置独立审查、替换专家的结构空间；后者须有真实委派或独立执行证据。**代价**是额外请求与上下文开销、文本交接失真和错误传播，以及过时记忆带来的偏差。本题只有两类工具计算，增加角色尚未展示准确率收益。

输出质量也须核验：模型对 QPSK、16QAM 阈值的说法不一致，且未逐一回答 BPSK、64QAM；这些只是课堂启发式建议，缺少目标 BER、编码与信道条件，不能视为通用工程门限。经理的总结也不自动等于有效复核。

## 4. 我自己的专业任务判断

**任务：本机代理链路异常诊断。** 输入为直连与代理请求的原始结果、当前规则和现象；输出为证据支持的原因判断、下一步检查及尚不能排除的情况。

**选择单 Agent + 两个工具：** 一个解析并比较出口 IP，另一个检查规则命中情况。两类证据服务于同一判断，上下文小，拆分角色会增加交接成本；接口还应区分“请求失败”和“出口相同”，避免把测不到当成没变化。即使 IP 相同，也不能单凭这一点断言代理失效。

若扩展到多站点采集与配置审计，出现稳定的职责边界，可采用双 Agent；若进一步需要多机器调查、动态分工和独立复核，再考虑 manager + specialists。结合第 6 章“观察—决策—执行—反馈”的思路，应先保证工具可靠、证据可追溯和任务闭环，再决定是否增加角色。**选型依据是拆分能否带来可验证收益，而不是任务看起来复杂或角色数量更多。**
