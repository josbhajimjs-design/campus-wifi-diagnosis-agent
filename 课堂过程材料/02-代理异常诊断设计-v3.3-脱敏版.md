## 项目一句话定义

`vpn_diag` 采集本机代理栈的四层证据，交给模型判读日志与分流规则配置的语义，
输出一句定位结论、支撑它的原始证据、以及下一步该查什么；
判不出来时，明确说卡在哪一层。它只读不改；AI 不决定查什么，也不被信任——
每条结论都要能指回具体的原始输出。

## 一、四层诊断模型（本项目的一等交付物）

这是整个项目真正的资产。工具只是这个模型的执行器，而模型本身可以独立成立。

| 层 | 这一层要回答的问题 | 检查项 | 证据形态 | 判定这层失败的条件 |
|---|---|---|---|---|
| **接管层** | 代理有没有接管流量 | 注册表的代理开关与端口；实际监听端口与属主进程；代理内核进程是否存在 | 注册表键值原文；`netstat` 行；进程名与 PID | 系统代理关闭；或注册表指向的端口没有进程在监听；或端口被非代理进程占用 |
| **规则层** | 进了代理之后，请求被谁放行 | **运行时**模式（`GET /configs`）；**运行时**规则列表（`GET /rules`，含每条规则的 `type` / `payload` / `proxy`）；有真实流量时用 `GET /connections` 看每条连接命中了哪条规则；内核日志里的失败记录 | 控制器返回的 JSON；内核日志里 `dial DIRECT (match RuleSet/xxx)` 这样的原文 | 模式为 direct；或目标域名命中 CN 规则集（本机实测命中 `cn_domain` / `cn_ip`）；或兜底 `Match` 指向节点组而实际走了 DIRECT |
| **网络层** | 流量有没有绕开代理 | 本机全局 IPv6 地址；内核 `ipv6` 开关的取值；TUN 模式状态；发起请求的应用是否读系统代理 | `Get-NetIPAddress` 输出；控制器 `GET /configs` 的 `ipv6` 字段；TUN 状态 | 存在全局 IPv6 且内核 `ipv6` 关闭；或应用不读系统代理（WSL / 虚拟机 / UWP / 自带网络栈） |
| **测量层** | 是不是测错了 | **先核对查询站有没有被规则 REJECT**；直连出口 IP 与走代理出口 IP 各一次（v4、v6）；同一目标连查两次看结果是否稳定 | `GET /rules` 里与查询站相关的条目；`curl.exe` 原始输出 | 查询站被 REJECT（测量本身失效，**不是代理坏了**）；或两个出口 IP 相同；或同一目标两次结果不同 |

排查顺序就是排除顺序：**接管层 → 规则层 → 网络层 → 测量层**。
上一层没有证据，不许往下走。判不出来时输出"已排除到第 N 层，缺什么证据"。

## 二、症状对照表（拿到现象之后先看这里）

| 你看到的现象 | 指向的层 | 去查什么 | 会拿到什么证据 |
|---|---|---|---|
| 节点显示已切换、延迟绿色，但浏览器查 IP 没变 | 测量层 → 接管层 | 直连与走代理的出口 IP 各查一次 | 两组 `curl` 原始输出；两者相同即为实锤 |
| 客户端界面显示"系统代理已开启"，但实际没生效 | 接管层 | 注册表 `ProxyEnable` 的真实取值 | 注册表键值原文（**界面会骗人，注册表不会**） |
| `curl` 走代理时直接连不上 | 接管层 | 注册表端口 vs 实际监听端口、属主进程 | 注册表键值；`netstat` 行；进程名与 PID |
| 日志里大量请求命中 `DIRECT` | 规则层 | 运行时模式、生效规则列表、命中记录 | 控制器 `GET /configs` 与 `GET /rules`；内核日志里的命中原文 |
| 浏览器能出去，某个应用出不去 | 网络层 | 那个应用是否读系统代理 | 进程清单；必要时该应用自己的代理设置 |
| 走代理时 IPv4 变了、IPv6 没变 | 网络层 | 全局 IPv6 地址；内核 `ipv6` 开关 | `Get-NetIPAddress` 输出；控制器 `GET /configs` 的 `ipv6` 字段 |
| 换个网站查 IP，结果不一样 | 测量层 | 同一目标连查两次，看结果是否稳定 | 两次 `curl` 原始输出 |

## 二·补、实测证据基线（本机核实，2026-09-16）

这一节每条都是在本机读出来的事实，不是推断。它是实现时的依据，也是验收时的对照物。

| 事实 | 值 |
|---|---|
| 客户端与版本 | Clash Verge Rev 2.5.2（`%APPDATA%\io.github.clash-verge-rev.clash-verge-rev`） |
| 端口 | `mixed-port: 7897`、`socks-port: 7898`、`port: 7899` |
| 控制器 | `external-controller: 127.0.0.1:9097`，另有命名管道 `\\.\pipe\verge-mihomo`，`secret` 可读 |
| 内核日志 | `logs/sidecar/sidecar_latest.log`（`logs/latest.log` 是 app 日志，两者不能混） |
| 内核 `ipv6` 开关 | `true` |
| TUN | `tun.enable: false` |
| 系统代理 | `enable_system_proxy: false`；注册表 `ProxyEnable=0`，残留 `ProxyServer=127.0.0.1:7897` |
| 内核日志级别 | `log-level: warning` |

### 控制器 API 活体验证结果（2026-09-16，Verge 已启动）

| 项 | 实测结果 |
|---|---|
| `GET /version` | `{"meta":true,"version":"v1.19.11"}` —— mihomo 内核 |
| `GET /configs` | 200，返回完整运行时配置：`"mode":"rule"`、`"ipv6":true`、`"log-level":"warning"`、`tun.enable=false`、`find-process-mode:"strict"` |
| `GET /rules` | 200，共 **66 条**：DomainSuffix 22、IPCIDR 20、Domain 18、RuleSet 4、AND 1、Match 1 |
| 单条规则字段 | `{"type":"Domain","payload":"api.ip.sb","proxy":"REJECT","size":-1}` |
| 兜底规则 | `[Match] -> [代理节点名称已隐去]`（默认走节点），前面是 `cn_domain -> DIRECT`、`cn_ip -> DIRECT` |
| 鉴权 | 不带密钥 401，错误密钥 401，正确密钥 200——工具可以明确区分"连不上"和"密钥不对" |
| `GET /connections` | 端点存在；无流量时 `connections` 为 `null`，字段结构待有真实流量时确认 |

**这组数据顺带印证了你最初的报告**：`cn_domain` 与 `cn_ip` 两条规则都指向 DIRECT，
这就是你说的"日志里大量请求命中 DIRECT 规则"的来源。
另外规则里有一条 `[AND] ((DstPort,443) && (Network,udp)) -> REJECT`，即 **QUIC / HTTP3 被拦**，
浏览器会回落 TCP——这一点在判断网络层时要考虑进去。

### 测量层基准线（2026-09-16，本机实测）

查询站：`https://www.cloudflare.com/cdn-cgi/trace`

| 请求方式 | 出口 IP | Cloudflare 判定位置 |
|---|---|---|
| 直连（`curl.exe` 不加 `-x`） | `[公网地址已隐去]` | `loc=CN` |
| 走代理（`-x http://127.0.0.1:7897`） | `[公网地址已隐去]` | `loc=US` |

三条结论：

1. **两个 IP 不同、国家也不同**——代理链路正常工作，出口确实跟随节点变化。
   工具测量层的核心判据（对比直连与走代理的出口）**已经被真实验证有效**
2. 这就是故障清单**测试 5「一切正常」的基准线**，已经拿到手
3. **你最初报告的入口症状在当前环境不复现**。所以验证不能靠"等它再犯"，
   只能靠主动构造——也就是故障清单测试 1–3，三个都是零成本（关系统代理、切 DIRECT 模式、退客户端）

查询站选型确定为 `https://www.cloudflare.com/cdn-cgi/trace`：不限流、
直接返回 `ip=` 与 `loc=`、且未被规则 REJECT。`api.ipify.org` 作废（限流）。

### 由实测得出的两条设计修正

**第一，规则层不能读 `config.yaml` 判断当前模式。** 三条理由：

1. 该文件开头写着 `# Generated by Clash Verge`——它是生成物，不是状态
2. 它的修改时间等于 app 启动时刻（`[Config] 生成运行时配置成功`），只在启动时写一次
3. 翻遍全部 app 日志，Verge **不记录模式切换**

**第二，规则层的命中记录不能只靠日志文件。** 因为 `log-level: warning` 意味着
内核日志里只有失败记录，正常完成的请求不会出现——
而"节点切了却没生效"的场景里，绝大多数请求恰恰是正常完成的。

日志里能拿到的证据形态长这样（本机真实存在）：

```
[TCP] dial DIRECT (match RuleSet/cn_domain) 127.0.0.1:49672 --> adxrp.admamax.com:443
    error: dial tcp [公网地址已隐去]:443: i/o timeout
```

它直接给出命中的规则名，是无可反驳的证据——但只在连接失败时才出现。

**结论**：运行时状态一律问控制器（`GET /configs` 拿模式和 `ipv6`、`GET /rules` 拿生效规则），
`config.yaml` 只在控制器不可用时兜底；日志文件用于拿"失败请求命中了哪条规则"这类线索。

### 第三条修正（v3.2 新增，也是最要命的一条）

**测量层必须先自检：我用来查出口 IP 的那个站点，本身有没有被规则拦掉。**

本机的规则里有四条 Domain 规则直接 REJECT 掉一批"查 IP"服务：

```
[Domain] api.ip.sb      -> REJECT
[Domain] ipapi.co       -> REJECT
[Domain] api.ipapi.is   -> REJECT
[Domain] ipwho.is       -> REJECT
```

后果很严重：如果工具拿 `api.ip.sb` 去测出口 IP，请求会被规则拦掉，
工具**测不到任何出口 IP**，然后很可能报出"代理不通"或"流量没走代理"——
而真实原因是**测量手段自己失效了**。这正是"测量层"这一层存在的意义，
也是必须把 `GET /rules` 纳入证据的原因：光看 curl 的输出，你永远分不清
"被规则拦了"和"代理坏了"。

**第四条修正（同一次验证中发现）：查询站还会限流。**

通过代理请求 `api.ipify.org`，拿到的是：

```
{"error": "Too Many Requests"}
```

一个真实的服务端响应，却不是一个 IP。如果工具不校验"响应里到底有没有 IP"，
它会拿到一段错误文本——而这段文本大概率会被当成一次失败的测量，
甚至被当成一个"IP 值"参与比较。

所以测量层的正确做法是三步，缺一不可：

1. 先从 `GET /rules` 里挑出**没有被 REJECT 的**查询站
2. 请求后**校验响应真的是一个 IP**（不是错误 JSON、不是空、不是 HTML）
3. 用两个不同的查询站**交叉验证**，结果一致才当作可信出口

**注意**：这次请求拿到了服务端响应，说明**代理链路本身是通的**。
我之前从开发沙箱发起的同类请求全部超时，那是我的沙箱限制，不是你的网络——
这一条我的判断错了，纠正。

## 三、AI 用在哪、不用在哪（防"套壳 AI"的边界）

| 脚本判定（二值事实，模型不许推翻） | 模型判读（规则引擎做不到的语义） | 明确不用 AI |
|---|---|---|
| 端口有没有在监听、属主是谁 | 日志尾部那一堆行到底在说什么 | 不做概率预测 |
| 注册表里代理开关的实际取值 | 规则列表里的哪一条可能命中你的目标域名 | 不做流量分类 |
| 两个出口 IP 是否相同 | 证据不足时，下一步该查什么 | 不决定查什么 |
| 本机有没有全局 IPv6 地址 | 把证据组织成一条能讲给人听的定位结论 | 不预测"大概是什么问题" |

这条边界是项目的成败线：如果采集全自动、判定靠规则、模型只负责把结论润色成人话，
那就是套壳 AI，评审会看穿。AI 必须落在规则引擎够不到的地方——
**读日志语义、读分流规则配置、以及诚实地报告自己的边界**。

## 四、主要行为

入口：`python vpn_diag.py`，无需参数。

1. **一次采集**：把四层的证据全部收齐，产出结构化证据包（每项带原始输出）
2. **一次判读**：证据包 + 分层纪律提示词交给模型，一次调用拿到结果
3. **固定四段输出**：结论（根因，或卡在哪一层）｜证据（带原始输出引用）｜
   下一步建议｜本次未覆盖的检查项

### 为什么不给模型配 tool-use 编排

v2 让模型自主决定"先查哪一项、下一步查什么"。放弃这个设计，因为：

- 检查项固定且只有 7 个，全部跑一遍只要几秒。**让模型决定查什么，等于让它重新发现一个已知的固定顺序**
- 多轮调用带来的是慢、贵、失败点多、难调试
- 省下的时间投给验证，而验证是这个项目里唯一不能省的东西

### 两道缰绳（硬约束）

- **分层纪律**：必须按四层顺序排除，上一层没证据不许往下走
- **证据绑定**：每条结论必须引用具体检查项的输出，引用不了的结论不许输出

## 五、故障清单与期望输出（提前定死的验收标准）

这一节是 CEO review 补上的，因为在 14 小时里它最容易被挤掉，而它恰恰是"判定准不准"的唯一证明。

| # | 怎么造出这个故障 | 期望工具的判断 | 必须引用的证据 |
|---|---|---|---|
| 1 | 关闭系统代理（**本机现状即是**，零成本） | 接管层失败：系统代理未开启 | 注册表 `ProxyEnable=0` 原文 |
| 2 | 在 Verge 里把模式切到 DIRECT | 接管层通过，但流量未经过节点 | 控制器 `GET /configs` 返回的运行时 `mode`（**不是** `config.yaml`） |
| 3 | 退出 Verge（内核停止、端口无监听） | 接管层失败：端口没有进程在监听 | `netstat` 无结果 + 进程清单 |
| 4 | 构造 IPv6 绕过（需本机有全局 IPv6；没有则记为"当前条件不可测"） | 网络层：IPv6 绕过了代理 | IPv4 两个出口不同、IPv6 两个出口相同的原始输出 |
| 5 | **一切正常**（节点生效） | 明确输出"未发现接管层问题"，**不许硬凑一个根因** | 两个出口 IP 不同的原始输出 |
| 6 | **让测量手段失效**：用 `api.ip.sb` 这种被 REJECT 的站点去测出口 IP | 识别为"**测量被分流规则拦截**"，而不是"代理坏了" | `GET /rules` 里 `api.ip.sb -> REJECT` 那一条 |

第 5 条是最重要的一条，**它是专门用来测幻觉的**：
当什么都没坏的时候，它敢不敢说什么都没坏。

第 6 条是免费送的——你现在的规则里本来就有，不用造。

## 六、范围边界

- **平台**：只做 Windows。用到注册表、`netstat -ano`、`curl.exe`
- **客户端**：不绑定某一款。采集器先"发现"客户端（扫已知配置目录），
  端口一律以系统代理注册表里的实际值为准
- **入口症状**：只处理"节点切换成功但出口 IP 未变"这一类，不处理断流、卡顿、DNS 污染
- **根因覆盖**：四层诊断模型
- **只读**：不修改系统设置、不自动修复、不重启客户端
- **依赖**：需要访问大模型 API；网络不通时退化为"只采集不判定"
- **时间盒**：14 小时（1 小时/天 × 14 天）

## 七、不做什么

- 不做 GUI
- 不做 tool-use 编排（见第四节，这是 v3 明确砍掉的）
- 不做自动修复、不改系统配置、不重启客户端
- 不抓包（不做 Wireshark 那一套）
- 不接控制器做可视化界面，但**要**接控制器取运行时状态（见第二·补节）
- 不覆盖 macOS / Linux
- 不做服务端、多用户、数据库
- 不在没有证据引用的情况下输出结论
- 不做对照诊断（见第九节，只写设计不实现）

## 八、风险与未定问题

1. **AI 沦为装饰（最大风险）**：缓解＝第三节那张边界表 + 第五节的第 5 条测试。
   验收时要专门跑一遍"一切正常"，看它敢不敢说什么都没坏。
2. **采集器工程膨胀**：多客户端、日志格式、规则解析会吞掉 AI 部分的时间。
   缓解＝时间盒固定 3.5 小时，超了就砍客户端数量，只保 Verge。
3. **验证时间被挤占**：第五节的清单必须做，它比任何代码都重要。
4. **API 死循环**：你是在代理出问题的时候用它，而它需要访问 API。
   优先选国内可直连的模型服务。
5. **已解决（v3.1）**：`config.yaml` 的 `mode` 不反映运行时模式，已由三条证据确认，
   设计改为读取控制器 API。剩余未定：模型与 `base_url` 具体选哪家。
6. **新发现（v3.1）**：`log-level: warning` 导致内核日志只有失败记录，
   正常请求的规则命中拿不到。缓解＝规则层以控制器 `GET /rules` 为主证据；
   确需实时命中流时用控制器的 `/logs` 流式接口（不改持久化配置）。
7. **新发现（v3.2）**：测量层的三个坑会让它得出完全错误的结论——
   ① 查询站被规则 REJECT（本机实测 4 个）；② 查询站限流，返回非 IP 的错误文本
   （本机实测 `api.ipify.org` 返回 `Too Many Requests`）；③ CDN 边缘地址或缓存。
   缓解＝测前核对 `GET /rules`、校验响应确实是 IP、双站交叉验证，
   并在结论里严格区分"测不到"和"没走代理"。
8. **部分验证（v3.3）**：测量层基准线已获取，出口 IP 确实随代理变化（见第二·补节）。
   仍未验证：`GET /connections` 的字段结构（采样时无流量）。实现阶段补测。
